Dialogs and overlays

When to use a dialog, menu, tooltip or a full page, and how overlays stack.

WCAG 2.2 AAPattern

  • When to use
  • Structure
  • States
  • Responsive behaviour

Overview

Overlays interrupt. Use the least interruptive one that fits.

When to use

NeedUse
Name a controlTooltip
Choose among a few actionsMenu
Confirm a destructive actionDialog (destructive)
Short form (1-3 fields)Dialog with form
View a photo largeLightbox dialog
Anything longer than a screenA page, not a dialog

Structure

A confirmation dialog, rendered inline for documentation.

Delete 3 photos?

They will be removed from the gallery and cannot be restored.

Heading names the action; the confirm button repeats it.

States

  • Opening moves focus to the first meaningful control (or the dialog heading) and makes the page inert.
  • Closing returns focus to the control that opened it.
  • Busy: the confirm button shows its busy state and Cancel stays available.
  • Failure: show an alert inside the dialog; do not close.

Responsive behaviour

  • Dialogs are 35rem wide, capped at viewport width minus 32px; the lightbox is 65rem.
  • On phones dialogs fill the width with the same padding and scroll the body, never the page behind.
  • Maximum height 90vh with an internally scrolling body.

Accessibility

  • WAI-ARIA Authoring Practices Dialog (modal): role="dialog", aria-modal="true", named by its heading (aria-labelledby).
  • Focus is trapped; Esc closes unless the dialog is mid-submit; backdrop click closes non-destructive dialogs only.
  • Use the native <dialog> with showModal() where possible.
  • Nothing outside the dialog is reachable by keyboard or screen reader while it is open.

Content

  • Heading is a question or action: "Delete 3 photos?".
  • Body states the consequence in one sentence.
  • Buttons: the safe action says Cancel; the other repeats the verb and object.
