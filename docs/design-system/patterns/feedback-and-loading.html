Feedback and loading

Which signal to use for which event, and how to show work in progress.

WCAG 2.2 AAPattern
  • Overview
  • When to use
  • Structure
  • States
  • Responsive behaviour
  • Accessibility
  • Content
  • Do and don't
  • Sources

Overview

Every action needs an answer. The right signal depends on how long the work takes and how much the person must act on the result.

When to use

SituationUse
Under 1s, local changeNothing; update the UI immediately
Short save or delete that succeededToast with Undo
Result that needs a decision or retryAlert next to the content
1-4s unknown wait on one elementSpinner or busy button
Page or list loadingSkeleton shaped like the content
Measurable work (uploads)Progress with a text status
Field problemInline message

States

  • Loading shows a skeleton for lists and cards (container aria-busy="true") and a busy button for actions. Reserve space to avoid layout shift.
  • Success toast (polite). Failure alert or inline error (assertive), persistent until dismissed or fixed.
  • Optimistic updates apply immediately and roll back with a toast if the server refuses.
  • Undo beats confirm for reversible actions; confirm only for irreversible ones.

Responsive behaviour

  • Toasts sit bottom-right on desktop and span the width above the safe area on phones.
  • Skeletons match the final grid so columns do not jump when content arrives.

Accessibility

  • Announce results: success in role="status", failure in role="alert" (4.1.3).
  • Progress uses a native <progress> with an accessible name and a text percentage.
  • Skeleton content is aria-hidden; the container is aria-busy.
  • Timed feedback lasts 8s or more and pauses on hover and focus (2.2.1).

Content

  • Past tense for success: "Session saved."
  • Failure says what is safe: "Finished photos are saved."
  • Progress text states counts: "4 of 6 photos uploaded".
