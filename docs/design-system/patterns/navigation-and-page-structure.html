Navigation and page structure

The shells, page headers and wayfinding shared by the public site, admin and client apps.

WCAG 2.2 AAPattern
  • Overview
  • When to use
  • Structure
  • States
  • Responsive behaviour
  • Accessibility
  • Content
  • Do and don't
  • Sources

Overview

Three apps, two shells: the public site uses the top bar and footer; admin and client use the sidebar workspace. Every page has one <h1> inside <main>.

When to use

  • Sidebar for six or more destinations that people move between all day (admin).
  • Top bar for five or fewer public destinations.
  • Tabs switch views of the same record (a gallery's photos / details); sub-pages are separate URLs.
  • Breadcrumb on any page two levels or deeper.

Structure

Workspace page header: eyebrow, title, description and the page's primary action.

  1. Sessions
  2. Wedding, Jun 6

Session

Wedding, Jun 6

Two photographers, 6 hours.

Breadcrumb, header with one primary action, then tabs.

States

  • Current page is marked with aria-current="page" in every nav.
  • Signed-out users see only open pages; coming-soon mode hides the marketing pages behind the blog.
  • On error or timeout the shell stays so the person can navigate away.

Responsive behaviour

  • Below 768px the public nav collapses into a menu button (aria-expanded) and the sidebar stacks above the content.
  • Page headers wrap: the primary action drops below the title and goes full width.
  • Tabs scroll horizontally rather than wrap.

Accessibility

  • Skip link first, then header, nav (with aria-label when there is more than one), main, footer (2.4.1).
  • Unique <title> per page: "Sessions | Studio admin" (2.4.2).
  • Consistent navigation order and names across pages (3.2.3, 3.2.4).
  • After client-side navigation move focus to the page heading and announce the title.

Content

  • Nav labels are plural nouns (Sessions, Photographers, Equipment).
  • Page titles name the screen, not the product.
  • Eyebrow names the area ("Admin", "Your galleries").
