Description list

A description list pairs short labels with values for one record: an inquiry, a session, a studio. It reads as a quiet sheet of facts.

WCAG 2.2 AAStatus: stableNative <dl>

Overview

Use a description list for the attributes of one thing on a detail page or in a side panel. Use a table to compare the same attributes across many records, and a form when people can edit the values.

  • Default sets a narrow label column beside a flexible value column, with a hairline between pairs.
  • Values can be plain text, a link (email, phone, map), a badge or several lines.
  • Group related facts in one list and separate groups with a heading, not an extra divider.

Anatomy

  1. Term (<dt>)Overline type in muted ink; a noun in sentence case that names the fact.
  2. Description (<dd>)The value in body-sm. Long values wrap with overflow-wrap: anywhere.
  3. Pair wrapper and dividerEach dt/dd pair sits in a <div> with a hairline bottom border; the last pair has none.

Variants

One structure, different values. Keep terms short so the 6rem label column does not wrap.

Sizes

A description list has a single size; it inherits body-sm from its container.

States

A description list is static, so it has no interaction states of its own. Values that are links or controls carry their own states; the matrix forces them.

  • Long values wrap anywhere, so an e-mail address or URL never overflows the panel.
  • Loading: replace each dd with a skeleton line and keep the terms visible so the layout does not jump.
  • Empty record: do not render the list; use an empty state.

Responsive behaviour

  • The label column is a fixed 6rem and the value takes the rest, which holds down to 320px for terms of up to about ten characters.
  • Longer terms ("Second photographer") wrap onto two lines; keep them short instead of widening the column.
  • In a two-column layout the list sits in the narrow column; below --layout-breakpoint-lg it moves under the main content at full width.
  • Never hide pairs on small screens; the list is already compact.

Theming

The list uses --color-fg-muted for terms, --color-fg-default for values and --color-border-default for dividers, so it follows light and dark with no overrides. Terms and values keep at least 4.5:1 on every surface that hosts them.

Accessibility

Role and pattern

Native <dl> with <dt> and <dd>, wrapping each pair in a <div> (valid HTML). No ARIA is needed; the browser exposes a description list and pairs terms with values. See the APG guidance on preferring native structure.

Keyboard

KeyAction
Tab / Shift+TabReaches only the interactive values (links, buttons) in DOM order.
EnterFollows a link value.
EscNo effect.

Focus

The list takes no focus. Link values show the shared 2px focus ring with 2px offset.

Labelling

Terms are the labels, so write them as complete nouns ("Email", not "E"). If the list needs a name, label it with aria-labelledby pointing at its heading. Never use a table or paragraphs with bold prefixes for the same job.

Motion

No motion.

Touch

Static text has no target. Link values should be at least 24px tall with 8px around them; on touch screens make phone and e-mail values a tappable link, not text to copy.

Content

  • Terms are nouns in sentence case without a colon: "Date", "Photographer".
  • Order facts by how people use them: who, what, when, where, then the rest.
  • Use the same term everywhere a fact appears: "Photographer", not "Shooter" in one place.
  • Dates and times follow the content foundation: "17 October 2026, 14:00".
  • Missing values show an em dash; add a hint in the value only when absence needs explaining.
