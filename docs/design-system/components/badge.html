Badge

A badge is a short status label: Scheduled, Delivered, Ready for review. It tells people where something stands without taking a line of its own.

Overview

Use a badge to show the state of a record in a table, a card or a photo tile. Use a chip when people can toggle or remove it, an alert for a message that needs attention, and a toast for a transient result.

  • Neutral is for plain classification (Draft, Base, Portrait).
  • Success, pending, error and info carry state. The word always says what the colour says.
  • One badge per row is usual; if a cell needs three, the data model needs a rethink, not a stack of badges.

Anatomy

  1. LabelOne to three words in sentence case, caption type. It is the accessible name; the colour never stands alone.
  2. ContainerPill with --radius-sm corners; background and ink come from the matching status pair.

Variants

Colour reinforces the word; it never replaces it. All five variants meet 4.5:1 for their text.

Sizes

A badge has one size (caption type, 4px by 8px padding); a larger label is a different component.

States

A badge is static: it has no hover, focus or disabled states. If it needs one, it is a chip or a button. The matrix shows each tone with and without a leading dot.

  • Dot: a decorative glyph before the word helps people who cannot tell the tones apart; it is aria-hidden.
  • Truncation: badges do not wrap or truncate (white-space: nowrap); keep labels short.
  • Loading: use a short skeleton line in the same cell instead of an empty badge.

Responsive behaviour

  • Badges keep their size at every width and never wrap internally.
  • In a table cell they stay on one line and the table scrolls (see table).
  • On a photo tile at 480px and below the badge moves from the top right to the bottom left so it does not collide with the select checkbox.

Theming

Each tone reads a background/foreground pair: --color-success-bg/-fg, --color-warning-bg/-fg, --color-danger-bg/-fg, --color-info-bg/-fg. The pairs are tuned per theme so contrast holds in dark mode. Neutral uses --color-bg-subtle-hover with default ink. The pending tone is backed by the warning tokens.

Accessibility

Role and pattern

Static text in a <span>. No role is needed. If the badge is the only change in a live region (for example a status that updates after review), put the region on the container with aria-live="polite"; the badge itself is not live.

Keyboard

KeyAction
TabA badge is not focusable.
Enter, SpaceNo effect.
EscNo effect.

Focus

A badge never takes focus. If a status needs explaining, the explanation is a visible hint or a link beside it, not a tooltip on the badge.

Labelling

The text is the name. Avoid colour-only badges, empty dots or abbreviations. A numeric badge such as "3" must carry meaning in text ("3 pending") or an aria-label.

Contrast

Success text on success background
Pending text on warning background
Error text on danger background
Info text on info background
Neutral text on neutral background

Motion

No motion. Do not pulse or flash a badge.

Touch

A badge is not a target. Do not place two interactive controls within 24px of a badge that looks like one.

Content

  • Use the status vocabulary from the domain: Draft, Scheduled, Ready for review, Delivered, Paid. One word where possible.
  • Sentence case, no trailing punctuation.
  • Say the state, not the action: "Delivered", not "Deliver".
  • Do not repeat the column header: in a Status column write "Delivered", not "Status: delivered".
  • Never use a badge for a long message. Use an inline message.
