Dialog

A dialog interrupts the page to ask one thing or show one thing. Everything behind it is inert until it closes.

WCAG 2.2 AAStatus: stableAPG Dialog (modal)Native <dialog>

Overview

Use a modal dialog when the person must decide or finish something before going on: confirm a deletion, name an album, look closely at one photograph. Do not use one for information that can stay in the page (use an alert or inline message), for a message that needs no answer (use a toast), or for a long task (use a page). See dialogs and overlays.

  • Default: a short question and two buttons. Sign out, discard changes, pause an upload.
  • Destructive confirm: names what will be lost; the danger button repeats the loss; the safe action is first and holds initial focus.
  • Form: one small form (rename an album, schedule availability). Larger forms get their own page.
  • Lightbox (.dialog--lg): one photograph at large size with previous and next. The only variant that needs arrow-key handling.

Use the native <dialog> element and open it with showModal(); that gives the backdrop, inert background, Esc and the top layer for free.

Anatomy

  1. Title.dialog__head h2: the dialog's accessible name through aria-labelledby.
  2. Close buttonIcon button with aria-label="Close dialog"; the same result as Esc.
  3. Body.dialog__body: one short message or form. Scrolls inside if it is taller than the viewport.
  4. Actions.form-actions: safe or cancelling action first, primary or danger action last.

Variants

All four dialogs on this page are static (dialog--static with open) so they render inline. In an application they are opened with showModal() and draw over a backdrop.

Sizes

Two widths exist. Medium is the default; large is for the lightbox and wide previews. Both shrink to 100vw - 2rem on small screens.

A small size is not defined: a confirmation that fits in less than 560px still reads better at that width.

States

The dialog itself is open or closed. What changes while it is open is its actions: busy while saving, disabled while invalid, failed after an error (shown in the variants above). The matrix shows the footer buttons in each state.

  • Open: the page behind is inert, the backdrop (--color-bg-backdrop) covers it, and focus is inside the dialog.
  • Busy: the pressed button shows its spinner and ignores clicks; the other buttons and Esc stay available unless the action cannot be cancelled, in which case disable them too and explain why.
  • Invalid: the field gets aria-invalid="true" and a message; focus moves to the first invalid field (see Failed submit above).
  • Failed: an alert with role="alert" at the top of the body; the dialog never closes on error.
  • Closing: always restore focus to the control that opened the dialog.

Responsive behaviour

  • The dialog is min(35rem, 100vw - 2rem) wide and centred; .dialog--lg is min(65rem, 100vw - 2rem). At 390px that leaves 16px each side.
  • Maximum height is 90vh; the body scrolls inside the dialog, and the head and actions stay reachable. Never let the page behind scroll.
  • Below 768px the horizontal padding drops to --space-5 in applications; when the content needs more than 90vh switch to a full-screen sheet, with the close button at the top left.
  • Buttons in .form-actions wrap; on a narrow dialog stack them with the primary action first in DOM order only if the app reverses visually; otherwise keep primary last.
  • In the lightbox the photograph scales with object-fit and the previous/next buttons stay visible at the foot.

Theming

The dialog surface is --color-bg-surface-raised with --shadow-4; the backdrop is --color-bg-backdrop, a translucent near-black in light and a stronger one in dark. In the dark theme the shadow is nearly invisible, so the raised surface (a lighter stone) carries the separation.

Accessibility

Role and pattern

WAI-ARIA APG Dialog (Modal). The native <dialog> opened with showModal() exposes role="dialog" and treats the rest of the page as inert, which is what aria-modal="true" promises. Set aria-modal="true" explicitly too for assistive technology that reads it, and use role="alertdialog" for destructive confirmations that need an immediate response.

Keyboard

KeyAction
TabMoves to the next control inside the dialog; from the last control it wraps to the first (focus trap).
Shift+TabMoves backwards; from the first control it wraps to the last.
EscCloses the dialog (the native cancel event) and restores focus to the opener. Block it only while a non-cancellable action runs.
EnterIn a form: submits. On a button: activates it.
SpaceActivates the focused button.
← / →Lightbox only: previous and next photograph. Do not intercept arrows when a text field has focus.

Focus

Trap: while open, focus cannot leave the dialog. showModal() makes the page inert, so Tab cycles inside; with a custom implementation, wrap focus at both ends. Initial focus: the first field in a form; the safe action ("Keep it") in a destructive confirmation; the first button otherwise; use autofocus on that element. Restore: on close, return focus to the element that opened the dialog, even if it moved; if it was removed, to the nearest sensible control (for example the list heading).

Labelling

Name the dialog with aria-labelledby pointing at its title (h2); the id must be unique on the page. Add aria-describedby pointing at the message paragraph for confirmations so the question is read on open. Unlabelled dialogs are announced as just "dialog". The close button has aria-label="Close dialog"; the backdrop is not a control and has no label.

Motion

Opening and closing do not animate by default. If a product fades the backdrop, use --duration-base with --ease-enter and drop the fade under prefers-reduced-motion. Never zoom or slide the dialog from off screen.

Touch

Buttons are 44px tall. The close button is 44px square at the top right. Do not close on a tap of the backdrop for forms with unsaved input; for confirmations it is acceptable but Esc and the close button must also work.

Content

  • Titles ask or state, sentence case, in plain language: "Delete this album?", "See you next time?".
  • The body says what will happen and what will not: "Your original session photographs will stay in your gallery."
  • Buttons are verbs naming the result: "Delete album", "Sign out", "Save name". Never "OK" or "Yes".
  • The cancelling button says what it keeps: "Keep it", "Stay here", "Keep editing".
  • One question per dialog. If it needs more than a short form, use a page.
  • Error text says what happened and that input was kept: "Your album could not be renamed. Your changes are still here. Try again."
