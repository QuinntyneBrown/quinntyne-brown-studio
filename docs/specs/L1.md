## 1. Purpose

This document defines the high-level requirements for Quinntyne Brown Studio, a photography studio management platform. It establishes the baseline for product review, detailed requirements, implementation, and acceptance testing.

The intended readers are the studio owner, product and design contributors, software engineers, and acceptance testers. “Shall” denotes a mandatory requirement. Draft status does not imply stakeholder approval or completed implementation.

## 2. Product scope and users

The platform comprises a public marketing website, an administrative web application, a client site, and a separately accessible design system. It supports photography discovery, indicative quotations, studio administration, session-photo review, and client access to photography deliverables.

| User | Intended capabilities |
| --- | --- |
| Public visitor / prospective client | View photography, calculate a live quote, and view print prices and package promotions. |
| Studio administrator | Manage public content, quotation inputs, schedules, equipment, preferred vendors, session photos, and AI-assisted photo review. |
| Authenticated client | View their session galleries, see print prices, request prints, and create albums. |
| Design and engineering contributor | Use the component catalog and implement traceable requirements through acceptance-test-driven development. |

Online payment, confirmed-booking workflows, invoicing, automated print fulfilment, and vendor procurement are not established by the source and are outside this baseline. Availability and advance-booking discounts are quotation capabilities; they do not establish a reservation workflow.

## 3. Source interpretation and terminology

| Term or interpretation | Meaning |
| --- | --- |
| Family portraits | Confirmed correction of “failing portraits” in the source. |
| Quote | A calculated estimate based on the supplied session details and administrator-managed pricing. A binding-contract workflow is not specified. |
| Advance-booking threshold | The minimum lead time used to assess an advance-booking discount; initially 90 days and configurable. |
| Slow day | A day eligible for a configured discount; the studio's eligibility rule remains an open decision. |
| Lunch cost | Interpretation of “prices in lunches” as a quotation cost input for lunches. |
| Session gallery | A collection of session photos made available to the associated client. Public-gallery selection is a separate administrative concern. |
| Album | A client-created collection of photos from accessible session galleries; physical album production is not specified. |
| GIVE / WHEN / THEN | Required acceptance-scenario labels: precondition, action or event, and observable outcome. |

Administrative access control, client isolation, basic validation, and visible failure outcomes in L2 are minimum derived requirements needed to make the source capabilities safe and testable. They do not prescribe an identity provider or expand the product into additional workflows.

## 4. High-level requirements

### L1-001 — Simple, responsive user experience

The platform shall provide radically simple, focused interfaces with generous white space. The public and administrative applications shall be responsive, and the product shall avoid features and interface complexity unrelated to the specified user tasks.

### L1-002 — Administrator-managed public presentation

The public application shall showcase photography using administrator-managed galleries and content, and shall present print pricing and package promotions with notice that promoted packages may change following detailed consultation.

### L1-003 — Live photography quotations

The public application shall calculate and update quotes live for weddings, events, headshots, and family portraits, accounting for multiple locations, equipment rental, potential parking costs, lunches, assistants, distance, and local studio fees.

### L1-004 — Configurable quotation discounts

The platform shall support quotation discounts through codes, advance booking, and slow-day booking. Administrators shall be able to configure advance-booking discounts and their lead-time threshold, initially 90 days.

### L1-005 — Pricing and studio configuration

Administrators shall be able to configure the rates that drive quotations, add studios and their applicable fees, and maintain print prices used by the public and client experiences.

### L1-006 — Photographer schedules and quote availability

Administrators shall be able to maintain photographer schedules, and the quoting experience shall use those schedules to determine the availability presented for requested photography sessions.

### L1-007 — Equipment and preferred-vendor management

Administrators shall be able to manage studio equipment and preferred vendors, including makeup artists, second shooters, and assistants.

### L1-008 — High-volume session-photo ingestion

Administrators shall be able to upload large batches of large photo files originating from cameras and associate the uploaded photos with photography sessions for subsequent review.

### L1-009 — Azure-assisted photo review

Administrators shall be able to review session photos and receive Azure AI suggestions identifying promising photos. AI output shall support the administrator's selection decisions.

### L1-010 — Authenticated client galleries

Clients shall be able to log in and view galleries from their photography sessions, with access restricted to the client content they are authorized to view.

### L1-011 — Client print requests and albums

Clients shall be able to view print prices, request prints of accessible session photos, and create albums from their accessible photos.

### L1-012 — Backend architecture

The backend shall use .NET, Clean Architecture, the latest freely usable version of MediatR applicable at dependency selection, and controller-based HTTP APIs rather than minimal API endpoint handlers.

### L1-013 — Frontend architecture

The frontend shall use Angular, BEM CSS naming, separate files per type and component concern, signals in preference to RxJS for reactive state, and a multi-project workspace containing components, API, domain, and application projects. Service consumers shall follow the referenced interface-driven consumption pattern.

### L1-014 — Design system as a product

The design system shall be maintained as a first-class product, list all platform UI components, and be deployable as a static web application, using the referenced design-system example as guidance.

### L1-015 — Backend acceptance-driven delivery

Backend behavior shall be developed using acceptance-test-driven development: a failing integration test with a faked database shall precede the simplest implementation that satisfies the behavior. Every acceptance criterion implemented fully or partially by the backend shall link to its corresponding acceptance test coverage.

### L1-016 — Frontend acceptance-driven delivery

Frontend behavior shall be developed using acceptance-test-driven development: a failing Playwright end-to-end test using Page Objects and a mocked backend shall precede the simplest implementation that satisfies the behavior. Every acceptance criterion implemented fully or partially by the frontend shall link to its corresponding acceptance test coverage.

## 5. Traceability and acceptance conventions

L1 identifiers are stable references. Each detailed requirement in [L2.md](L2.md) has one primary L1 parent and one or more uniquely identified acceptance criteria. The [traceability matrix](L2.md#3-traceability-matrix) provides navigation from each L1 to all of its L2 children.

Acceptance criteria define observable behavior or verifiable engineering evidence. Architecture and development-process criteria are checked through source, configuration, build, and test-history evidence where a UI scenario is not appropriate. Requirements and criteria are not claims that implementation or tests already exist.
