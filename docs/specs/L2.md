## 1. Purpose and conventions

This document decomposes the high-level requirements into implementable obligations and verifiable acceptance criteria. Each L2 has exactly one primary L1 parent. “Shall” denotes a mandatory requirement.

Acceptance identifiers use `AC-L2-NNN-NN` and remain stable when tests are added. Each scenario uses the requested **GIVE**, **WHEN**, and **THEN** labels. “GIVE” states the precondition; “WHEN” describes an action or event; “THEN” defines the observable result. Multiple outcomes in a scenario must all hold.

Unless a scenario explicitly exercises invalid data or access failure, its preconditions include an authorized user and valid configured data. Configuration changes are evaluated on subsequent reads or calculations; simultaneous live propagation across open browsers is not required by the source.

Where a criterion depends on an unresolved business rule or numerical target, it identifies the relevant decision from [L1's decision register](L1.md#6-decisions-outstanding). Such criteria are conditional on that decision being resolved and cannot be marked accepted using an arbitrary implementation default.

At implementation time, record coverage against each applicable acceptance ID with the implementing layer, status (`Not implemented`, `Partial`, or `Complete`), relative test-file link, and test name. For partial implementation, state the uncovered behavior. If both layers implement a criterion, provide evidence for both. No test links are fabricated in this requirements baseline.

## 2. Detailed requirements and acceptance criteria

### L2-001 — Responsive public and administrative applications

**Parent:** [L1-001](L1.md#l1-001--simple-responsive-user-experience)

The public and administrative applications shall support their specified tasks across the agreed desktop, tablet, and mobile viewport matrix.

**AC-L2-001-01**

- **GIVE** the supported browser and viewport matrix has been agreed under OD-08.
- **WHEN** a user views and operates each applicable page at every supported viewport.
- **THEN** content and controls remain readable and usable without clipping or overlapping controls, and the page's primary task can be completed.

### L2-002 — Focused visual design

**Parent:** [L1-001](L1.md#l1-001--simple-responsive-user-experience)

The platform's interfaces shall use generous white space, clear task hierarchy, and controls limited to the specified workflows.

**AC-L2-002-01**

- **GIVE** an approved visual reference and task inventory have been recorded under OD-08.
- **WHEN** a page is reviewed against that reference and inventory.
- **THEN** its spacing and visual hierarchy conform to the reference, and every action control supports a specified task.

### L2-003 — Restricted administrative access

**Parent:** [L1-001](L1.md#l1-001--simple-responsive-user-experience)

The platform shall restrict administrative content and operations to authorized studio administrators. This is a derived access requirement for the administrative application.

**AC-L2-003-01**

- **GIVE** a visitor is unauthenticated or is authenticated only as a client.
- **WHEN** they attempt to access an administrative page or invoke its operation directly.
- **THEN** administrative data is not disclosed and administrative changes are not performed.

### L2-004 — Public photography galleries

**Parent:** [L1-002](L1.md#l1-002--administrator-managed-public-presentation)

The public application shall display the photography galleries configured for public presentation by an administrator.

**AC-L2-004-01**

- **GIVE** an administrator has selected a gallery and its photos for public presentation.
- **WHEN** a visitor opens that gallery.
- **THEN** the configured photos are displayed without requiring client login, and photos not selected for public presentation are absent.

### L2-005 — Public content and gallery administration

**Parent:** [L1-002](L1.md#l1-002--administrator-managed-public-presentation)

Administrators shall be able to update marketing content and configure public galleries through the administrative application without editing application code.

**AC-L2-005-01**

- **GIVE** existing public content and a configured gallery.
- **WHEN** an administrator saves a content change and changes the gallery's selected photos.
- **THEN** a subsequent public page load shows the saved content and gallery selection.

### L2-006 — Public print prices

**Parent:** [L1-002](L1.md#l1-002--administrator-managed-public-presentation)

The public application shall display administrator-configured print options and their prices.

**AC-L2-006-01**

- **GIVE** print options and prices are configured.
- **WHEN** a visitor views print pricing.
- **THEN** each presented option is associated with its current configured price.

### L2-007 — Package promotions and consultation notice

**Parent:** [L1-002](L1.md#l1-002--administrator-managed-public-presentation)

Administrators shall be able to maintain public package promotions, and the public application shall state that the promoted offer is subject to change after detailed consultation.

**AC-L2-007-01**

- **GIVE** an administrator has saved a package promotion.
- **WHEN** a visitor views the promotion.
- **THEN** its configured details and the consultation qualification are visible together.

### L2-008 — Supported photography services

**Parent:** [L1-003](L1.md#l1-003--live-photography-quotations)

The quote calculator shall support weddings, events, headshots, and family portraits using the configured rates for the selected service.

**AC-L2-008-01**

- **GIVE** each of the four services has valid rate configuration.
- **WHEN** a visitor selects each service in turn and supplies its required quote inputs.
- **THEN** the calculator can produce a quote using the rates for that selected service.

### L2-009 — Location and travel costs

**Parent:** [L1-003](L1.md#l1-003--live-photography-quotations)

The calculator shall support multiple session locations and account for distance, potential parking costs, and applicable local studio fees using configured pricing rules.

**AC-L2-009-01**

- **GIVE** OD-01 is resolved and a two-location example has independently calculated distance, parking, and studio charges.
- **WHEN** the visitor supplies those locations and applicable cost inputs.
- **THEN** the calculated quote includes those charges according to the agreed rules without omitting or duplicating a location's costs.

**AC-L2-009-02**

- **GIVE** a valid quote has optional parking or studio charges and the configured rules allow those charges to be absent.
- **WHEN** the corresponding parking need or studio selection is removed.
- **THEN** the resulting quote excludes the charges that no longer apply.

### L2-010 — Equipment, lunch, and assistant costs

**Parent:** [L1-003](L1.md#l1-003--live-photography-quotations)

The calculator shall account for applicable equipment rental, lunch, and assistant costs.

**AC-L2-010-01**

- **GIVE** OD-01 is resolved and a session example includes independently calculated equipment rental, lunch, and assistant costs.
- **WHEN** the visitor calculates a quote for that example.
- **THEN** the quote includes each applicable cost according to the configured rules and matches the expected calculation.

### L2-011 — Live recalculation

**Parent:** [L1-003](L1.md#l1-003--live-photography-quotations)

The calculator shall update the displayed quote as valid pricing inputs change, without requiring a full page reload or a separate quote-submission workflow.

**AC-L2-011-01**

- **GIVE** a valid quote is displayed.
- **WHEN** the visitor changes a pricing input and the recalculation completes.
- **THEN** the displayed amount reflects the latest valid inputs without a page reload.

**AC-L2-011-02**

- **GIVE** multiple input changes produce calculations that finish out of order.
- **WHEN** an earlier calculation finishes after the calculation for the latest inputs.
- **THEN** the earlier result does not replace the quote for the latest inputs.

### L2-012 — Incomplete inputs and calculation failures

**Parent:** [L1-003](L1.md#l1-003--live-photography-quotations)

The calculator shall distinguish a valid current quote from incomplete inputs, invalid inputs, missing rate configuration, or a failed calculation.

**AC-L2-012-01**

- **GIVE** a required input is missing or violates its agreed validation rule.
- **WHEN** the calculator evaluates the inputs.
- **THEN** it identifies the input requiring correction and does not represent an old amount as a valid quote for those inputs.

**AC-L2-012-02**

- **GIVE** inputs are valid but required pricing configuration is missing or calculation fails.
- **WHEN** the calculator attempts to produce a quote.
- **THEN** it displays that the quote cannot currently be calculated and does not present a fabricated amount.

### L2-013 — Quote presentation

**Parent:** [L1-003](L1.md#l1-003--live-photography-quotations)

The calculator shall present the calculated estimate with the pricing currency and any applied discount identified.

**AC-L2-013-01**

- **GIVE** pricing conventions under OD-01 are resolved and a valid quote has been calculated.
- **WHEN** the result is displayed.
- **THEN** the estimate, currency, and any applied discount are visible and agree with the calculated result.

### L2-014 — Discount codes

**Parent:** [L1-004](L1.md#l1-004--configurable-quotation-discounts)

The calculator shall accept discount codes and apply the corresponding discount only when the code satisfies the configured eligibility rules. Managing these rules is a derived configuration need.

**AC-L2-014-01**

- **GIVE** code rules under OD-02 are resolved and a code is eligible for the current quote.
- **WHEN** the visitor applies that code.
- **THEN** the quote is recalculated with the configured code discount and identifies the discount applied.

**AC-L2-014-02**

- **GIVE** a code is unknown or ineligible under the configured rules.
- **WHEN** the visitor attempts to apply it.
- **THEN** the code grants no discount and the interface explains that it cannot be applied.

### L2-015 — Advance-booking configuration and eligibility

**Parent:** [L1-004](L1.md#l1-004--configurable-quotation-discounts)

Administrators shall be able to configure the advance-booking discount and its lead-time threshold, with an initial threshold of 90 days. The calculator shall evaluate eligibility using the requested session date and the agreed date rules.

**AC-L2-015-01**

- **GIVE** the advance-booking configuration has not been customized.
- **WHEN** an administrator views the threshold.
- **THEN** it is 90 days and can be changed and saved.

**AC-L2-015-02**

- **GIVE** OD-02 date rules are resolved, an advance discount is configured, and the threshold is N days.
- **WHEN** otherwise identical quotes are evaluated for lead times of N minus one, N, and N plus one days.
- **THEN** the advance discount is ineligible below N and eligible at or above N, subject to the agreed discount-combination rules.

**AC-L2-015-03**

- **GIVE** an administrator changes and saves the lead-time threshold.
- **WHEN** a subsequent quote is evaluated.
- **THEN** eligibility uses the saved threshold rather than the previous threshold.

### L2-016 — Slow-day discounts

**Parent:** [L1-004](L1.md#l1-004--configurable-quotation-discounts)

The platform shall support configuration of slow-day discount eligibility and value, and the calculator shall evaluate the requested session date against that configuration.

**AC-L2-016-01**

- **GIVE** OD-02 is resolved and a slow-day discount rule is configured.
- **WHEN** quotes are evaluated for one eligible date and one ineligible date.
- **THEN** only the eligible quote qualifies for the slow-day discount, subject to the agreed discount-combination rules.

### L2-017 — Consistent discount combinations

**Parent:** [L1-004](L1.md#l1-004--configurable-quotation-discounts)

The calculator shall apply the agreed discount-combination rules consistently when multiple discounts qualify and shall remove eligibility when changed inputs no longer qualify.

**AC-L2-017-01**

- **GIVE** OD-02 combination rules are resolved and a quote qualifies for a code, advance-booking, and slow-day discount.
- **WHEN** the quote is calculated repeatedly with the same inputs and configuration.
- **THEN** the applied discounts and total match the agreed combination rules on every calculation.

**AC-L2-017-02**

- **GIVE** a quote currently receives a date-dependent discount.
- **WHEN** the visitor changes the session date so that the discount no longer qualifies.
- **THEN** the recalculated quote no longer applies that discount.

**AC-L2-018-02**

### L2-026 — Bulk upload of large camera photos

**Parent:** [L1-008](L1.md#l1-008--high-volume-session-photo-ingestion)

Administrators shall be able to upload a batch of large photo files originating from a camera without submitting each file individually.

**AC-L2-026-01**

- **WHEN** an administrator uploads a supported batch at the agreed batch-count boundary containing files at the agreed size boundary.

### L2-027 — Session association

**Parent:** [L1-008](L1.md#l1-008--high-volume-session-photo-ingestion)

Uploaded photos shall be associated with the intended photography session and remain distinguishable from photos in other sessions.

**AC-L2-027-01**

- **GIVE** two photography sessions exist.
- **WHEN** an administrator uploads a batch to one session and opens both sessions for review.
- **THEN** the uploaded photos appear in the selected session and are not attributed to the other session.

### L2-028 — Upload status and failures

**Parent:** [L1-008](L1.md#l1-008--high-volume-session-photo-ingestion)

The upload experience shall report progress and distinguish successful files from rejected or failed files without presenting an incomplete batch as wholly successful.

**AC-L2-028-01**

- **GIVE** OD-04 is resolved and a batch includes valid files and an unsupported or oversized file.
- **WHEN** the batch is processed.
- **THEN** progress is visible, successful uploads are identified, and the rejected file is identified with its reason.

**AC-L2-028-02**

- **GIVE** a batch is uploading and some files have completed.
- **WHEN** a transfer failure interrupts the remaining files.
- **THEN** the interface distinguishes completed files from incomplete or failed files and does not claim that the entire batch succeeded.

**AC-L2-029-01**

### L2-030 — Azure AI photo suggestions

**Parent:** [L1-009](L1.md#l1-009--azure-assisted-photo-review)

The session review experience shall use an Azure AI service to suggest promising photos and shall identify suggestions as AI-generated guidance rather than an administrator's final decision.

**AC-L2-030-01**

- **GIVE** OD-05 is resolved and the configured Azure AI service returns suggestions for a session's photos.
- **WHEN** analysis results are presented to the administrator.
- **THEN** suggested photos can be identified, suggestions are labelled as AI-generated, and the results are associated with the correct session photos.

**AC-L2-030-02**

- **GIVE** an AI suggestion has been received for a private session photo.
- **WHEN** the analysis result is processed.
- **THEN** the suggestion alone does not publish the photo to the public gallery or alter client access.

### L2-031 — AI unavailability

**Parent:** [L1-009](L1.md#l1-009--azure-assisted-photo-review)

An AI analysis failure shall be visible to the administrator and shall not prevent manual review of successfully uploaded photos.

**AC-L2-031-01**

- **GIVE** session photos are available and the Azure AI analysis fails or is unavailable.
- **WHEN** an administrator uses session review.
- **THEN** the analysis failure is indicated, no fabricated suggestions are presented, and the photos remain available for manual inspection.

### L2-034 — Client content isolation

**AC-L2-044-01**

### L2-045 — Interface-driven service consumption

**Parent:** [L1-013](L1.md#l1-013--frontend-architecture)

Frontend service consumers shall depend on interfaces and Angular injection tokens so production services can be replaced by mocks without changing consumer code, following the [source-referenced pattern](https://github.com/QuinntyneBrown/interface-driven-service-consumption).

**AC-L2-045-01**

- **GIVE** a consumer uses a service contract with production and mock implementations.
- **WHEN** the host switches the token's provider from the production implementation to the mock implementation.
- **THEN** the unchanged consumer operates through the same contract and does not import or instantiate the concrete service implementation.

### L2-049 — Backend test-first acceptance workflow

**Parent:** [L1-015](L1.md#l1-015--backend-acceptance-driven-delivery)

**AC-L2-049-01**

- **GIVE** an acceptance criterion is selected for backend implementation.
- **WHEN** the increment's recorded development evidence is reviewed.
- **THEN** evidence shows the corresponding integration test failing for the missing behavior before implementation and passing after implementation, and the change is limited to satisfying the specified behavior.

### L2-050 — Faked database in backend acceptance tests

**Parent:** [L1-015](L1.md#l1-015--backend-acceptance-driven-delivery)

- **GIVE** the backend acceptance-test host uses a database fake and no external database is available.
- **WHEN** an acceptance test invokes an implemented HTTP operation.
- **THEN** it exercises the controller and application behavior against controlled fake data and verifies the expected response or observable state change without a live database connection.

### L2-051 — Backend acceptance-test traceability

## 4. Review and acceptance checklist

- Every source capability and implementation constraint is represented by an L1 and one or more L2 requirements.
- Every L2 has one linked L1 parent, a mandatory statement, and at least one uniquely identified GIVE / WHEN / THEN criterion.
- Every L1 has children in the traceability matrix; every L2 appears in that matrix exactly once.
- Outstanding decisions affecting a criterion are resolved and recorded before the criterion is accepted.
- Fully or partially implemented backend and frontend behavior has linked acceptance-test coverage; partial coverage identifies the remaining gap.
- Engineering constraints have review or build evidence as appropriate; behavior tests do not substitute for architecture or test-first process evidence.
